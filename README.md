# FERMA

Первая версия платформы для готового контента. Один профиль автора/проекта — до двух соцсетей: YouTube, TikTok, Instagram, Threads и X.

## Реализовано
- Профили, поиск и фильтры; два слота с ограничениями в базе данных.
- Загрузка нескольких готовых видео/изображений в приватное R2-хранилище (MP4/MOV/JPEG/PNG/WebP, до 90 МБ на файл).
- Медиатека, предпросмотр, сохранение и редактирование черновиков.
- Серверный адаптер Zernio: импорт уже подключённых соцсетей, передача медиа и планирование постов. Авторизация соцсетей выполняется в самом Zernio.
- Свой адрес почты у каждого профиля и чтение входящих писем через MailClaw.
- Профиль считается готовым с одной подключённой соцсетью из двух возможных.
- Часовой пояс Asia/Qyzylorda (UTC+5).
- Приватный доступ Sites и проверка владельца каждой записи. Ключ Zernio передаётся владельцу только по явному нажатию «Показать».

## Docker Desktop — отдельный проект `ferma`

Из этой папки (`platform`):

```powershell
docker compose up -d --build
docker compose ps
```

Открыть http://localhost:3100. В Docker Desktop появится отдельный проект `ferma`, сервис `app`. Порт опубликован только на `127.0.0.1`; сеть и том `ferma_data` создаются отдельно от других проектов.

Контейнер запускает собранное приложение через локальный Workers runtime (Wrangler/workerd). База D1 (SQLite) и файлы R2 эмулируются локально в постоянном томе `/data`. Миграции применяются при запуске с учётом уже выполненных миграций. Пересборка и пересоздание контейнера сохраняют данные.

Это локальное рабочее пространство одного владельца: Docker-шлюз устанавливает отдельную идентичность `ferma_docker_owner`, проверяет Host/Origin и удаляет входящие заголовки идентичности. Облачные данные и вход ChatGPT не переносятся. Для публичного размещения этой версии требуется отдельная авторизация; текущая конфигурация предназначена для работы на этом компьютере.

Для подключения Zernio откройте **Профили → нужный профиль → API-ключ Zernio** и нажмите **Проверить и сохранить**. У каждого профиля свой ключ, которым выполняются только чтение его соцсетей, загрузки в Zernio, планирование и обновление статусов. После сохранения ключа и при открытии карточки аккаунты автоматически загружаются из Zernio; ручное обновление доступно рядом со списком. Один ключ нельзя назначить двум профилям одного владельца. В «Настройках» отображается список профилей со статусами ключей.

Ключи зашифрованы AES-GCM с привязкой к владельцу и профилю. В карточке есть отдельные поля **Сохранённый ключ** и **Новый ключ**. Кнопка **Показать** запрашивает сохранённое значение только для владельца, через POST с проверкой Origin и запретом кэширования; обычный список профилей не содержит ключей. **Скрыть** убирает значение из состояния формы.

Новый действительный ключ может принадлежать другому кабинету Zernio. Если у него нет доступа к прежнему удалённому профилю, привязка и соцсети сбрасываются атомарно с заменой ключа, затем импортируются новые. В черновиках нужно заново выбрать сети; отправленные публикации остаются в прежнем кабинете и помечаются соответствующим статусом для ручной проверки. Неверный или дублирующий ключ сохраняемый ключ не меняет. Пока публикация непосредственно отправляется, замена временно отклоняется; повторите после завершения отправки.

Ключ шифрования находится в `/data/secrets/settings.key`; резервируйте весь том. Общий `ZERNIO_API_KEY` и прежняя таблица `integrations` больше не используются; старые данные не удаляются и не назначаются профилям автоматически.

Управление:

```powershell
docker compose logs --tail 100 app
docker compose stop
docker compose start
# После изменения исходников:
docker compose up -d --build
```

`docker compose down` удаляет контейнер и сеть, сохраняя том. Флаг `-v` удаляет также базу и загруженные файлы.

Проверка шлюза: `node --test docker/gateway.test.mjs`. Healthcheck проверяет API и доступ к базе.

Справка: [локальные данные Workers](https://developers.cloudflare.com/workers/local-development/local-data/), [публикация портов Docker](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/).

В карточке профиля доступна форма изменения имени (меняется имя только в FERMA). Если ключу доступны несколько профилей Zernio, выберите нужный. Если подключено больше двух поддерживаемых аккаунтов или несколько одной соцсети, выберите до двух разных соцсетей. Выбор запоминается. Синхронизация обновляет имена и статусы, убирает удалённые в Zernio аккаунты, не создаёт профили и не запускает OAuth. При ошибке API сохранённый список не очищается.

## Почта профиля (MailClaw)

У каждого профиля свой адрес на вашем домене, например `kvartira@mail.example.com`. Письма принимает [MailClaw](https://github.com/missuo/mailclaw) на Cloudflare, а FERMA запрашивает их через его API. Сейчас доступны только приём и чтение: отправки и скачивания вложений нет.

Письма из интернета нельзя принимать только на этом компьютере, поэтому MailClaw разворачивается отдельно:

1. Подключите к Cloudflare домен или поддомен. Email Routing заменяет его MX-записи, поэтому не используйте домен с уже работающей почтой.
2. Разверните MailClaw по его README. Дополнительно выполните `bun run r2:create`: в шагах README этого нет, а хранилище вложений обязательно.
3. В Cloudflare: **Email → Email Routing → Routing rules → Catch-all → Send to a Worker → mailclaw**.
4. В FERMA: **Настройки → Почта** укажите адрес сервиса (только `https://`), домен и `API_TOKEN`, затем нажмите **Проверить и подключить**.
5. В карточке профиля задайте имя адреса. Пока карточка открыта, список писем обновляется каждые 20 секунд.

Токен шифруется и в браузер не передаётся. Он открывает весь домен, поэтому FERMA запрашивает письма только по адресу профиля и повторно проверяет получателя при открытии письма. HTML писем показывается в изолированном `iframe` без скриптов, форм и внешних картинок. При смене домена в настройках адреса всех профилей переходят на новый домен.

Отправитель должен писать адрес в нижнем регистре: MailClaw ищет получателя по точному совпадению.

## Локальный запуск без Docker
Node.js 22.13+.

```powershell
npm ci
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_stiff_moonstone.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_zernio_settings.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0002_profile_zernio_keys.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0003_remote_profile_isolation.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0004_imported_account_selection.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0005_profile_mail.sql
npm run dev -- --host 127.0.0.1
```

Миграции применяются однократно, последовательно. Локальный вход эмулирует только одного пользователя на loopback. Он отсутствует в production; не публикуйте dev-сервер в интернет.

Для запуска без Docker задайте в игнорируемом `.dev.vars` постоянный `SETTINGS_ENCRYPTION_KEY` — 32 случайных байта в Base64 — и перезапустите сервер. Сами ключи Zernio вводятся в профилях через интерфейс. В Docker ключ шифрования создаётся автоматически.

## Границы первой версии
- Пока секрет не настроен, профили, загрузки и черновики работают; реальные подключения и планирование недоступны.
- Нет генерации контента, аналитики, пакетного назначения одного поста десяткам профилей, командных ролей и встроенного видеоредактора.
- Файлы хранятся в приватном R2. При планировании сервер копирует выбранный файл в хранилище Zernio через presign API.
- Публикации выполняет расписание Zernio. Кнопка обновления получает статусы; вебхуки ещё не подключены.
- Частичные и неуспешные публикации отображаются отдельно. Неопределённый сетевой результат сохраняет исходный payload и повторяется с тем же Idempotency-Key. После времени публикации повтор блокируется для ручной сверки в Zernio.
- Если процесс аварийно завершится после блокировки отправки, запись `sending` требует сверки с Zernio перед восстановлением. Это не выдаётся за успешную публикацию.
- Ограничения форматов, прав, числа аккаунтов и тарифа проверяются Zernio и соцсетями. Реальные публикации необходимо проверить после добавления ключа на ваших аккаунтах.

## Обновление интерфейса
- Системный Segoe UI, как на сайте Гудини; SVG-логотипы соцсетей Simple Icons (CC0, лицензия в public/icons).
- Единая нейтральная палитра, сетка отступов, границы, иконки и состояния фокуса.
- Компактный список профилей с переключением на карточки, поиск по клавише `/`, сброс фильтров.
- Фильтрация публикаций по профилю, статусу и поисковой строке; отдельный статус «Требуют внимания».
- Загруженный из редактора файл автоматически назначается черновику; удаление черновика требует подтверждения.
- Навигация сохраняет выбранный раздел в URL; адаптивная нижняя панель на телефоне.
- Проверены список/карточки, поиск, автоматическое назначение загрузки, пустой экран и мобильная форма на ширине 390px.
- 18 насыщенных цветов профиля, произвольный цвет и HEX-код; контраст букв подбирается автоматически.
- Ввод и проверка отдельного ключа Zernio в каждом профиле; изоляция ключей, подключений и публикаций.
